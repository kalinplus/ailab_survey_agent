# EviSurvey 单请求版 DataFlow 与 DataModel 规范

## 0. 核心设计

EviSurvey 是一个面向任意学术主题的可信综述生成 Harness。

本版本采用 **Single Knowledge-Build Request** 设计：

```text
A 不再反复给 B 发 search / parse / paper card / taxonomy 多个请求。
A 只给 B 发一个 KnowledgeBuildRequest。
B 内部自己完成论文检索、PDF 解析、MinerU 图文抽取、PaperCard 构建、EvidenceStore 构建、Taxonomy 构建和 CitationIndex 构建。
B 最后一次性返回 KnowledgeBundle。
```

也就是说，模块职责变成：

```text
A = Controller / Orchestrator
B = Knowledge Pipeline Worker
C = Grounded Survey Writer & Report Renderer
```

------

# 1. 总体流程

## 1.1 人话版流程

```text
用户输入一个主题，例如：
"The development of OCR"

A 先理解用户需求。
A 生成任务说明和搜索策略。
A 把整个知识构建任务一次性交给 B。

B 收到一个总请求后，内部自己完成：
1. 搜论文
2. 下载或读取 PDF
3. 调 MinerU 解析 PDF
4. 抽取正文、图、表、caption
5. 生成 PaperCards
6. 生成 EvidenceStore
7. 生成 FigureBank / TableBank
8. 生成 Taxonomy
9. 生成 CitationIndex
10. 返回完整 KnowledgeBundle

A 收到 KnowledgeBundle 后：
1. 检查格式
2. 检查 paper_id 是否一致
3. 检查 evidence 是否存在
4. 检查 citation 是否完整
5. 生成 CitationReadySet

然后 A 把 CitationReadySet + KnowledgeBundle 交给 C。
C 在证据约束下生成综述和图文报告。

最后 A 再让 B 对 C 的 survey.md 做后验验证：
1. 引用是否合法
2. 图片是否合法
3. claim 是否有证据

如果不通过，A 让 C 修改。
如果通过，C 渲染最终 HTML/PDF。
```

------

## 1.2 完整 DataFlow

```text
User Topic
  ↓
A: TaskRequest
  ↓
A: SearchStrategy
  ↓
A → B: KnowledgeBuildRequest
  ↓
B 内部执行 Knowledge Pipeline:
    Search Papers
    ↓
    Fetch / Load PDFs
    ↓
    MinerU Parse PDFs
    ↓
    Build ParsedPapers
    ↓
    Build FigureBank
    ↓
    Build TableBank
    ↓
    Build PaperCards
    ↓
    Build EvidenceStore
    ↓
    Build Taxonomy
    ↓
    Build CitationIndex
    ↓
    Build KnowledgeBundle
  ↓
B → A: KnowledgeBundle
  ↓
A: Validate KnowledgeBundle
  ↓
A: CitationReadySet
  ↓
A → C: SurveyGenerationRequest
  ↓
C → A: SurveyMarkdown + Timeline
  ↓
A → B: VerificationRequest
  ↓
B → A: CitationResult + ClaimMap
  ↓
如果失败：
    A → C: RevisionRequest
    C → A: RevisedSurvey
    A → B: VerificationRequest
  ↓
如果通过：
    A → C: EvaluationRenderRequest
  ↓
C → A: EvaluationReport + HTML + PDF
  ↓
A: FinalState
```

# 3. 模块职责

## 3.1 A：Orchestrator

A 负责：

```text
1. 接收用户输入。
2. 生成 task_request.json。
3. 生成 search_strategy.json。
4. 生成一个 knowledge_build_request.json 给 B。
5. 接收 B 返回的 knowledge_bundle.json。
6. 校验 knowledge_bundle 的完整性和一致性。
7. 生成 citation_ready_set.json。
8. 生成 survey_generation_request.json 给 C。
9. 生成 verification_request.json 给 B。
10. 如果验证失败，生成 revision_request.json 给 C。
11. 生成 evaluation_render_request.json 给 C。
12. 输出 final_state.json。
```

A 不负责：

```text
1. 不直接搜论文。
2. 不直接调 MinerU。
3. 不直接生成 PaperCards。
4. 不直接写 survey 正文。
5. 不直接判断论文内容真假。
```

------

## 3.2 B：Knowledge Pipeline Worker

B 收到一个 `knowledge_build_request.json` 后，内部完成整条知识构建 pipeline。

B 负责：

```text
1. 根据 search_strategy 搜论文。
2. 使用 seed fallback。
3. 获取 PDF。
4. 调 MinerU 解析 PDF。
5. 生成 parsed_papers。
6. 生成 figure_bank。
7. 生成 table_bank。
8. 生成 paper_cards。
9. 生成 evidence_store。
10. 生成 taxonomy。
11. 生成 citation_index。
12. 打包 knowledge_bundle。
13. 在 survey 生成后，执行 citation verification 和 claim mapping。
```

------

## 3.3 C：Survey & Report Worker

C 负责：

```text
1. 根据 survey_generation_request 写 survey.md。
2. 只能使用 citation_ready_set 中的引用。
3. 只能使用 figure_bank 中的图片。
4. 只能使用 table_bank 中的表格。
5. 生成 timeline.json。
6. 如果 A 要求修订，生成 survey_revised.md。
7. 根据 citation_result 和 claim_map 生成 evaluation_report。
8. 渲染 final_report.html / final_report.pdf。
```

## 5.3 Optional A-Internal Strategy Probing

在 full mode、配置了 `SCIVERSE_API_TOKEN`（兼容 `SCIVERSE_API_KEY` / `SCIVERSE_API`），且显式设置 `STRATEGY_PROBING_ENABLED=true` 时，A 的 `search_strategy_builder` 可以在内部执行轻量 pre-search probing：

```text
1. 用 Sciverse `agentic-search` API 抓取少量与主题相关的文献证据片段和元数据。
2. 对标题和摘要做轻量向量化。
3. 用 K-Means 风格聚类发现当前领域的候选主题簇。
4. 从每个主题簇中抽取关键词和代表论文。
5. 仍然序列化为原版 search_strategy.json。
```

这个过程只发生在 A 内部，不改变 `SearchStrategy` datamodel。B 仍然只读取：

```text
cache/search_strategy.json
```

如果没有 API key、未开启 probing、API 失败、返回摘要不足，A 自动回退到规则版策略生成。A 不构建 PaperCard、不生成 EvidenceStore，也不替代 B 的正式检索。


## 16.3 Optional Skill Fields

为了支持 A 侧统一管理 Skills，所有 A 发给 B/C 的 request 都允许新增可选字段：

```json
{
  "active_skills": [
    {
      "name": "string",
      "description": "string",
      "path": "skills/<skill_name>/SKILL.md",
      "applies_to": ["string"],
      "owner": "A | B | C",
      "load_mode": "stage_scoped",
      "purpose": "string"
    }
  ],
  "skill_policy": {
    "progressive_disclosure": true,
    "load_index_first": true,
    "only_load_stage_relevant_skills": true,
    "request_scoped_activation": true,
    "unload_after_stage": true
  }
}
```

规则：

```text
1. active_skills 不改变原有 inputs / outputs，只是阶段性 SOP 指针。
2. A 负责生成 cache/skill_manifest.json，并根据当前 stage 选择 active_skills。
3. B/C 如果内部调用 LLM，应读取 active_skills 中的 SKILL.md；如果是纯规则程序，可以忽略该字段。
4. 不把所有 skill 正文一次性注入上下文，只在当前阶段按需加载，避免上下文过载。
5. 一个 request 执行结束后，本阶段 active_skills 自动失效。
```

当前推荐映射：

```text
knowledge_build_request: knowledge_build, paper_card
survey_generation_request: survey_writing, artifact_generation
verification_request: citation_verification
revision_request: survey_revision
evaluation_render_request: evaluation, artifact_generation, report_rendering
```

```text

12. ClaimMap 必须在 survey.md 生成后由 B 构建。
13. paper_id 一旦生成，后续不许改。
14. aspect_id 一旦生成，后续不许改。
15. category_id 一旦生成，后续不许改。
```

# 24. 答辩说法

```text
我们没有把 B 拆成多个来回调用的小工具，而是把 B 设计成一个 Knowledge Pipeline Worker。A 只向 B 发起一次 KnowledgeBuildRequest，B 在内部完成论文检索、PDF 获取、MinerU 图文解析、PaperCard 构建、EvidenceStore 构建、Taxonomy 构建和 CitationIndex 构建，并最终返回一个 KnowledgeBundle。这样减少了跨模块通信复杂度，同时保留了完整的中间 artifacts，方便 A 做一致性检查和 C 做图文并茂的 grounded survey generation。
```

------

# 25. 最终一句话

```text
单请求版的核心是：A 只负责“发任务、验结果、锁引用、调写作”；B 负责“一次性完成知识构建全流程”；C 负责“在锁定引用和多模态证据上生成并渲染综述”。这样既减少联调复杂度，又保留了可追踪、可验证、图文并茂的 Harness 特征。
```
