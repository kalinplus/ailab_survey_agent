# 综述初稿可用性改进计划

> **状态（2026-09-08 更新）**：本文档是改进前的诊断快照。批次一已修复问题 1（gate 失败 → `quality_failed` + 非零退出，真跑验证）与 P5 哨兵串；批次二已落地 claim 切分归一统一内核与 claim 结构化前置（真跑验证：claim_map 41 = 结构化源 41，两侧绑定一致）；canonical 死因已确诊（17/20 死于检索召回层：别名+年份查询无效、精确年份过滤错杀——修法见 PROGRESS.md 2026-09-08 Log）；MinerU 根因已实测确认（agent 接口异步未轮询、v4 可用但未下载 zip）。以下"当前最重要的问题"各节描述的是**立项时**的状态，读时以此为准。

## 目标

目标不是让系统直接生成可发表论文，而是让用户输入一个主题后，系统能够产出一份**结构完整、论断有证据、引用可追溯、经典工作覆盖基本完整**的综述初稿。人工核查后主要做事实抽样、术语修正和少量文字润色，不需要大规模重写正文或重建参考文献。

当前项目已经具备完整流水线：Module A 负责规划和调度，Module B 负责检索与证据构建，Module C 负责写作、核查、修复和渲染。单元测试当前为 `380 passed, 1 skipped`，说明工程接口和规则逻辑较稳定；但这不等于真实 API、真实 NLI 和真实 LLM 下的综述质量已经达标。

## 当前最重要的问题

### 1. 质量失败仍被报告为成功

当前 `output/final_state.json` 显示：

- `status: completed`
- `goal_gate.passed: false`
- `stop_reason: repair_budget_exhausted`
- `unsupported: 11`
- `invalid_citations: 1`

`output/review_report.json` 的最终结论是 `public_but_not_submission_ready`，evidence grounding 只有 `0.233`，低于 `0.8` 的硬门槛。

原因在 `harness/agent_loop.py:168-188`：Goal Gate 失败后仍继续渲染，并把最终状态写成 `completed`。`main.py:67-70` 只要状态是 `completed` 就返回退出码 0。因此调用方可能把“生成了文件”误认为“质量验收通过”。

**改进：**明确区分 `prepared`、`completed`、`quality_failed`、`partial_success` 和 `failed`。Goal Gate 未通过时不得报告 `completed`，CLI 必须返回非零退出码，并在最终报告中直接显示失败原因。

**验收：**构造一个仍有 unsupported claim 的运行，确认：状态不是 `completed`、退出码非零、HTML/PDF 可以保留但明确标记不可交付。

### 2. 引用存在，但正文论断没有被充分支持

当前 `output/evaluation_report.json` 显示：

- `citation_validity_score: 0.975`
- `evidence_grounding_score: 0.233`
- supported claims: `3`
- weak claims: `1`
- unsupported claims: `11`
- total claims: `15`

这说明“引用格式合法”与“论断确实由证据支持”是两件不同的事。当前生成侧的 claim map、修复侧的 claim 分组和评测侧的句子切分/归一化没有完全共享同一套规则，导致同一篇文档在不同阶段可能得到不同的 claim 数和支持结论。

**改进：**统一 claim/evidence 协议。写作阶段不应让 LLM 直接自由生成带引用的最终 Markdown，再由下游反解析；应先生成结构化的 claim、evidence id 和支持范围，再渲染为正文。例如每条 claim 至少包含：`claim_text`、`evidence_ids`、`support_scope`、`section_id`。生成、修复和评测都使用同一套句子切分、引用归一化和 evidence window。

**验收：**同一份草稿经过生成侧和评测侧处理后，claim 数、引用归属和支持状态能够逐条对账；任一 unsupported claim 都能定位到 section、sentence 和 evidence id。evidence grounding 达到至少 `0.8`，且不能靠大量删除 claim 达成。

### 3. 领域经典论文没有稳定进入最终语料

最新四层评测中，seed-bib recall 为 `0.304`，canonical hit rate 为 `3/20`。Dreamer、MuZero、World Models、PlaNet 等地标工作仍然缺失。

问题不一定发生在检索阶段，也可能发生在后续的相关性预过滤、排序、论文数量上限、core paper 截断或 citation whitelist 阶段。现在只有最终缺失清单，不能说明每篇论文在哪一环被丢掉。

**改进：**为每篇 canonical paper 建立存活记录，至少跟踪：

```text
canonical title / aliases
→ search hit
→ relevance prefilter
→ ranking
→ corpus retained
→ paper card
→ evidence available
→ citation-ready whitelist
→ cited or excluded reason
```

对主题相关的经典论文设置硬保留或可解释排除机制，不能让普通 recency 排序静默淘汰它们。

**验收：**每篇 canonical paper 都有最终状态和排除原因；相关的核心论文至少能进入语料和 citation-ready set。canonical hit rate 先达到 `12/20` 以上，再继续扩大普通论文数量。

### 4. 证据深度不足，导致正文像摘要拼接

`main.py:23-26` 表明 MinerU 默认关闭；`tools/knowledge_pipeline_worker.py:125-141` 表明真实 NLI 也需要显式开启。当前许多论文最终只有摘要级信息，摘要可以支持贡献概述，但不能可靠支持实验细节、方法差异、局限性和跨论文比较。

这与 L3 评委指出的“内容薄”“依赖 abstract snippets”“placeholder text”“future directions generic”直接对应。P5 中的占位 limitation 也曾泄漏到正文。

**改进：**按证据层级限制可生成的句子类型：

- `fulltext_verified`：可以生成方法细节、实验、比较和局限；
- `abstract_only`：只允许生成贡献和任务概述；
- `parse_failed`：不生成具体学术判断。

全文解析预算优先给 core papers；非核心论文可以保留摘要证据。建卡阶段不得写入“需要更深解析”一类哨兵文本。

**验收：**所有方法比较、实验结论和局限性句子都能绑定全文证据；正文不再出现哨兵串；每个核心 section 至少有若干篇全文证据。

### 5. 运行产物可能来自不同轮次

当前项目曾记录 `output/` 混合不同运行工件的问题。`cache/` 和 `output/` 是共享目录，运行会直接覆盖 `knowledge_bundle`、`evidence_store`、`paper_cards`、`taxonomy`、`survey` 和评测报告。这样会出现正文来自一次运行、证据库来自另一次运行的情况，评测数字无法可靠复现。

**改进：**每次运行使用独立目录，例如：

```text
runs/<task_id>/<run_id>/cache/
runs/<task_id>/<run_id>/output/
runs/<task_id>/<run_id>/logs/
```

最终公开文件可以复制到 `output/`，但报告必须记录 `task_id`、`run_id`、输入输出文件 hash 和运行配置。

**验收：**任意 `evaluation_report.json` 都能反查到唯一的 survey、evidence store、paper cards 和 taxonomy；重新运行不会覆盖旧运行的证据链。

### 6. 默认路径与真实质量路径没有被清楚区分

默认模式是 `demo`；默认 NLI 是 FakeNLIModel；MinerU 默认关闭；修复 Agent 通过 `EVISURVEY_REPAIR_AGENT` 开关控制。README 中的“运行成功”容易被理解为“真实质量已经验证”。

**改进：**每次 `final_state.json` 写入完整 execution profile，包括：运行模式、真实/模拟 NLI、MinerU 是否启用、writer LLM、repair agent、是否使用 seed papers、是否使用实时 SciVerse。将 demo、full、full-real-verify、submission 作为明确的运行配置，而不是只依赖散落的环境变量。

**验收：**报告读者不查看环境变量也能判断本次结果是否经过真实 NLI、真实 SciVerse 和真实全文解析；submission profile 未通过 hard gate 时不能标记为可提交。

## 改进顺序

### 阶段一：先修正状态和工件一致性

先处理质量失败误报和跨运行污染，不先扩展 Agent 能力。

- 修正最终状态机和 CLI 退出码；
- 增加 `quality_failed` 等明确状态；
- 引入 run isolation；
- 为报告记录运行配置和 artifact hash。

这是第一优先级，因为没有可信的成功/失败信号，后续指标和实验都无法可靠比较。

### 阶段二：统一 claim/evidence 生成协议

- 统一生成侧、修复侧和评测侧的句子切分与 citation normalization；
- 将 claim 与 evidence id 前置绑定；
- 禁止依赖最终 Markdown 的正则反解析作为唯一事实来源；
- 保留每条 claim 的状态变更记录。

目标是先把 evidence grounding 从“能测出来”变成“能稳定改善”。

### 阶段三：补齐 canonical paper 存活链

- 建立 canonical paper 状态表；
- 对相关地标工作设置硬保留或可解释排除；
- 记录每一环的淘汰原因；
- 通过 per-aspect 最低覆盖保证综述骨架完整。

目标是先覆盖领域骨架，再增加普通论文数量。

### 阶段四：提高核心论文证据深度

- core papers 优先全文解析；
- 为 evidence 设置 `fulltext_verified`、`abstract_only`、`parse_failed`；
- 按证据层级限制正文表述；
- 修复 MinerU 成功判定，不能把 HTTP 200 当成解析成功。

目标是让方法、实验、比较和局限段落不再只是摘要改写。

### 阶段五：稳定 taxonomy、LLM 和质量评测

- 固定 taxonomy 的数量和结构约束；
- 记录 fallback、重试、超时和空回复；
- 对 GLM 单独配置预算、超时和输出 schema；
- 将冗余从句子级检查提升到 section 职责和 claim ownership 检查。

目标是降低跨 run 波动，而不是继续堆更多 Agent。

## 暂时不优先做的事情

- 不把主流程完全交给 LLM 自由编排；固定主流程目前更容易复现和诊断。
- 不继续增加 Agent 数量来掩盖 evidence grounding 问题。
- 不把 citation validity 当成 grounding 的替代指标。
- 不先追求更多图表或更复杂视觉效果；当前视觉产出已不是主要瓶颈。
- 不把 `FINAL_SEED_PAPERS` 产物当作实时检索质量证明；它只用于可复现展示。

## 最终交付判据

只有同时满足以下条件，才把运行标记为 `completed` 或 `submission_ready`：

1. Goal Gate 通过，且 `invalid_citations = 0`；
2. evidence grounding 达到目标阈值，建议先设为 `>= 0.8`；
3. 生成侧与评测侧 claim 能逐条对账；
4. canonical paper 有可解释的保留或排除记录，核心地标不再静默缺失；
5. 核心 section 的方法、比较、实验和局限论断都有相应证据；
6. 正文不含哨兵串、内部 ID、过程性元话语或不可解释的占位内容；
7. survey、evidence store、paper cards、taxonomy、评测报告和 HTML/PDF 属于同一个 run；
8. 真实 SciVerse、真实 NLI 和实际目标运行配置至少完成一次端到端验收；
9. 人工抽样核查后不需要大规模删除、重写或补建参考文献。

最终标准不是“程序退出 0”，而是：系统能够诚实报告质量状态，并稳定地产出一篇证据链完整、领域骨架基本齐全、人工只需轻量修改的综述初稿。
